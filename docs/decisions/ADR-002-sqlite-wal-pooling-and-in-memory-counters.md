# ADR-002: SQLite 读写分离、WAL 模式与原子状态计数优化

## 1. 决策背景 (Context)
在 Legado Server 服务端，SQLite 作为唯一的轻量级持久化存储引擎，承载了书源配置、书架数据、用户鉴权、封面缓存以及整书离线章节分片。
在高并发搜索与多章节离线下载（整书数千章写入）时，传统的 SQLite 默认配置（Rollback Journal + 单连接争用）会导致严重的数据库锁死（`SQLITE_BUSY`）与吞吐急剧下降。

## 2. 裁定方案 (Decision)
1. **SQLite WAL 模式与参数优化**：
   - 启用 `JournalMode.WAL`（预写日志模式），实现读写互不阻塞。
   - 配置 `SynchronousMode.NORMAL`，大幅提升批量写入 IOPS。
   - 设置 `busyTimeout = 10000ms`，防止偶发并发锁等待超时。
2. **连接生命周期与读写分离**：
   - **写操作**：采用单个专用的长生命周期连接，配合 `ReentrantLock` 严格串行化写入，彻底消除写写争用。
   - **读操作**：采用基于 `ConcurrentLinkedQueue` 的无锁轻量连接池（上限 16 个读连接），支持高并发并发读取。
3. **消除高频统计 SQL，改用内存原子计数与节流入库**：
   - 在整书离线缓存（`BookCacheService`）中，严禁每下载一章执行一次 `SELECT COUNT(*)`。
   - 采用内存 `AtomicInteger` 维护已下载章节计数，仅在每 1000ms 节流窗口向数据库更新一次进度元数据。

## 3. 备选方案与否决理由 (Alternatives Considered & Why Rejected)

- **备选方案 A：引入 MySQL / PostgreSQL 等外部数据库**
  - *否决理由*：极大增加用户部署复杂度（违反单容器开箱即用原则），增加运维负担；对于个人与家庭书库，优化后的 SQLite 性能绰绰有余。
- **备选方案 B：每次下载章节均即时全量事务提交**
  - *否决理由*：在下载 3,000 章小说时将产生 3,000 次磁盘事务，严重阻塞 SQLite 写锁；节流合并写入将磁盘写事务降低 90% 以上。

## 4. 后果与权衡 (Consequences & Trade-offs)

### 正面收益
- 彻底解决高并发搜索与离线下载时的 `SQLITE_BUSY` 数据库锁死报错。
- 整书下载吞吐提升 5~10 倍，单机支持多个书籍后台同时缓存。
- 维持极简的单文件 SQLite 持久化，备份与迁移仅需拷贝 `.data/` 目录。

### 负面代价
- 服务端意外强制断电时，最近 1 秒内的缓存进度数字可能存在极小滞后（但章节内容文件已持久化，重新打开时通过 O(1) 预查即可自动纠正）。
