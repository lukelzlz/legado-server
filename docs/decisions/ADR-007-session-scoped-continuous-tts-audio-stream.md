# ADR-007: 采用服务端会话级连续 MP3 音频流与独立进度事件通道

## 1. 决策背景 (Context)

ADR-006 已确定在线 TTS 使用服务端代理、句子级切分和预缓冲。但当前实现的每句 `/api/tts/speak` 会返回完整 `ByteArray`，前端再创建 Blob URL 并切换 `HTMLAudioElement`。在移动端后台，这种短请求和媒体源切换容易被浏览器暂停，无法稳定维持跨句、跨章节播放。

新的需求同时要求：保持现有的句子切分和播放控制体验；Edge-TTS 与自定义 HTTP TTS 都由服务端请求；一次朗读会话跨章节使用一条持续音频流；句子高亮仍然准确；暂停、跳句和点击定位仍可用；服务端状态只保存在内存。

## 2. 裁定方案 (Decision)

### 2.1 三通道会话模型

为一个在线朗读会话建立一个内存 `TtsSession`，使用三个同源通道：

1. **控制通道**：JSON HTTP 请求负责创建会话、追加 chunk、暂停/继续、定位重建和停止，沿用现有登录、Session Cookie 与 CSRF 校验。
2. **音频通道**：浏览器通过会话音频地址发起一个长连接 `GET`，服务端以 `audio/mpeg` streaming response 写入连续 MP3 数据。前端继续使用原生 `HTMLAudioElement`，但 `src` 绑定流地址，不再为每个 chunk 创建 Blob URL。
3. **进度通道**：浏览器通过会话事件地址建立 SSE，服务端发送结构化的 chunk/章节状态事件。事件至少包含会话代际、chunk 标识、章节索引、段落索引、状态和错误信息，以维持现有高亮及自动连播状态机。

音频与 SSE 是独立连接：SSE 中断可以单独恢复，不得停止已经可播放的音频；音频中断则按最近确认的 chunk 重建播放会话。会话 ID 使用随机不可预测值，并绑定创建该会话的认证用户。

### 2.2 服务端队列与上游请求

前端继续负责文本净化和句子切分，提交的每个 chunk 保留现有文本、voice、rate、pitch 以及 custom TTS 参数。服务端把 chunk 放入有界队列，并按顺序消费：

- Edge-TTS 复用现有 WebSocket 握手、SSML 转义、`muid`、协议版本和异常中止逻辑；上游收到的音频数据可在接收时写入会话输出，不等待整章。
- 自定义 HTTP TTS 复用现有模板替换、Header 代理和 GET/POST 逻辑，但输出必须是可连续拼接的 MP3（`audio/mpeg`）。服务端不引入音频转码；非兼容格式明确失败。
- 同一会话只允许一个上游 chunk 消费任务，保证音频顺序和进度事件顺序稳定。待处理队列有长度上限；重复定位使用新的会话代际/游标，使旧任务的结果不可写入当前输出。

### 2.3 播放控制语义

- **开始/追加**：创建会话并绑定音频流后，客户端按当前状态机追加后续 chunk；正常跨章节只追加新章节队列，不更换音频元素。
- **暂停/继续**：客户端暂停/继续 `HTMLAudioElement`，服务端暂停/恢复从队列取新上游任务，避免无界合成。已写入浏览器缓冲区的数据允许自然播放或由浏览器暂停。
- **跳句/点击段落/上一句/下一句**：取消旧会话的未完成任务，建立新的会话代际和音频流，从目标 chunk 开始；旧流的回调和元数据不得更新当前播放器。
- **自然结束**：当前章节有下一章且自动连播开启时，追加下一章；达到睡眠定时或全书结束时，关闭队列并发出结束事件。
- **断线恢复**：客户端记录最近确认完成的 chunk。音频错误时从该 chunk 恢复，最多重复当前句一次；连续失败进入暂停/错误状态，禁止无限自动重试。

### 2.4 生命周期与资源安全

`TtsSession` 只存在内存，包含有界 chunk 队列、音频输出通道、SSE 事件流、取消句柄、当前代际和最后活动时间。以下任一条件发生时，服务端必须取消上游 HTTP/WebSocket、关闭音频与事件通道、清空队列并移除会话：客户端停止、连接断开、认证失效、上游异常、空闲超时、最大生命周期到达或应用停止。

所有异步写入都必须检查会话仍存活且代际匹配；取消属于正常控制流，不应被记录为未处理服务端错误。

## 3. 备选方案与否决理由 (Alternatives Considered & Why Rejected)

### 备选方案 A：继续每句返回完整 Blob

- **否决理由**：移动端仍需频繁发起请求和切换媒体源，无法解决后台挂起、跨句断音和跨章连接不稳定的问题。

### 备选方案 B：一次性合成整章或整场音频文件

- **否决理由**：首字延迟高、内存和带宽峰值大，无法保持句子级点击定位，也会让跨章和睡眠定时变得笨重。

### 备选方案 C：前端使用 Web Audio/MediaSource 手工拼接所有音频片段

- **否决理由**：需要客户端处理 MP3 分片、缓冲、暂停和生命周期，移动端后台兼容性更复杂；原生 `HTMLAudioElement` 直接消费服务端长流更符合锁屏媒体通道。

### 备选方案 D：使用 WebSocket 同时承载控制、音频和元数据

- **否决理由**：浏览器原生音频元素无法直接把 WebSocket 二进制消息作为媒体源播放；若再引入 MediaSource，会重新承担客户端复用和后台兼容复杂度。HTTP 音频长流、HTTP 控制和 SSE 事件更贴合现有 Ktor 路由与请求模型。

### 备选方案 E：为自定义 TTS 引入服务端统一转码

- **否决理由**：引入 ffmpeg 或其他重量级运行时会增加 Docker 体积、CPU 消耗和部署变量；本期通过明确要求可拼接 MP3 控制输入范围。

## 4. 后果与权衡 (Consequences & Trade-offs)

### 正面收益 (Pros)

1. 浏览器在线 TTS 从多个短媒体请求变成一个持续音频源，更适合 Android Chrome、iOS Safari/PWA 的后台和锁屏媒体播放。
2. 服务端统一掌握 Edge/custom 上游请求、顺序、取消和鉴权，客户端继续使用现有播放器状态与高亮模型。
3. 句子元数据与音频数据分离，连续 MP3 不需要在音频字节中嵌入前端专用控制信息。
4. 内存会话无需修改 SQLite，定位和跨章追加可以保持低延迟。

### 负面代价与应对 (Cons & Mitigations)

1. 单个会话会长期占用音频连接、事件连接和内存队列。
   - **应对**：队列有界、空闲/最大生命周期可控，关闭时统一取消上游和清理会话。
2. 连续 MP3 对自定义 TTS 的格式要求更严格。
   - **应对**：只接受明确可拼接的 `audio/mpeg`，对不兼容响应返回可诊断错误，不做隐式转码。
3. 音频和 SSE 存在独立时序，网络断线可能让 UI 元数据暂时落后或重复当前句。
   - **应对**：使用会话代际、chunk 游标和幂等状态更新；恢复时最多重复当前句，禁止旧会话覆盖新状态。
4. 移动端后台行为仍受浏览器和操作系统策略影响。
   - **应对**：要求用户手势启动，使用原生媒体元素和 MediaSession；不承诺浏览器/PWA 被强制结束后的播放。

## 5. 需要验证的实现假设

- Ktor 当前依赖能够提供带背压、可取消的 `audio/mpeg` 响应写入方式，并能在客户端断开时取消会话协程。
- Edge-TTS 接收回调中的 MP3 音频帧可以安全转发；自定义源的响应需要在进入队列前验证内容类型和可拼接约束。
- 原生 `HTMLAudioElement` 在目标浏览器中可以携带同源 Session Cookie 请求会话音频地址，并在用户手势后继续后台播放。
- 现有 MediaSession、阅读器高亮和跨章状态机可以通过进度事件接入，而无需改变用户可见操作语义。
