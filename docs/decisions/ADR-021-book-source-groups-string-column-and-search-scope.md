# ADR-021: 书源分组以字符串列落库与分组范围搜索语义

## 1. 决策背景 (Context)

Legado 书源的 `bookSourceGroup` 在手机端就是一个字符串（可以理解为「源上的一个标签」）。服务端已把它落在 `source.source_group` 列，但围绕它需要一组**长期生效的语义决策**，否则每次碰这块都会重新纠结：

1. 分组要不要**独立成表**（`source_group` + 关联表），以支持一个源属于多个分组、分组排序、分组颜色等？
2. 「未分组」怎么表达？库里既有 `null` 也有 `''`，搜索范围里怎么选？
3. 分组名比较**大小写敏感**吗？改名撞上已有分组怎么办？
4. 删除分组时，组内书源怎么办？
5. 分组范围与「指定单个书源」是什么关系？同时给了会怎样？
6. `POST /api/search` 原本有个「源数 > 20 就只取前 20」的上限，选了分组还套用吗？

---

## 2. 裁定方案 (Decision)

1. **分组就是 `source.source_group` 这一列字符串，不建独立表（No Group Table）**：
   - 聚合列表、改名、删除全部是对 `source` 表的 `group by` / `update`，零新增表、零迁移；
   - 代价是「一个源只属于一个分组」、且没有分组排序/颜色。这在 Legado 语义里是可接受的：手机端的分组同样是源上的字符串，多分组字符串（`A,B`）**原样保留、整体比较**，不做拆分（拆分等于悄悄改写用户数据）。
2. **「未分组」是一个哨兵值，不是一个真分组**：
   - 服务端 `SourceGroupFilter.UNGROUPED = "__ungrouped__"`，翻译为 `source_group is null or trim(source_group) = ''`；
   - 同时覆盖 `null` 与空串两种落库形态（真实数据两种都有）；
   - `listSourceGroups()` **不返回**「未分组」这一行 —— 它不是一个分组，而是「还没有分组」的状态，由前端单独提供选项卡。
3. **分组聚合/比较一律 `trim()` + `collate nocase`**：
   - `trim()`：导入数据里存在带首尾空格的分组名，不 trim 会把一个分组拆成两个；
   - `nocase`：范围过滤天然大小写不敏感，若列表区分大小写，就会出现「显示两组、点任一组都命中两组」的自相矛盾；
   - 因此 `listSourceGroups` 用 `group by trim(source_group) collate nocase`，`renameSourceGroup` / `clearSourceGroup` / 搜索过滤统一 `where source_group = ? collate nocase`。
4. **改名撞上已有分组 = 合并（Merge, Don't Block）**：
   - 不做重名拦截。书源分组不是用户手建的实体，合并是两个分组「同名」的必然结果；拦下来反而要求用户先去把另一组清空。返回值如实报告受影响书源数，前端提示就是「已将 N 个书源从 A 移到 B」。
5. **删除分组 = 解绑（Soft Unbind），绝不删书源**：
   - `clearSourceGroup` 只做 `set source_group = null`，与书架分组删除同源（见 ADR-009 / AGENTS 部落知识）；
   - 删组后这些源会出现在「未分组」范围里继续可搜，不会变成「搜不到的死源」。
6. **范围语义：分组与单源互斥，且「全部书源」永远是默认项**：
   - 前端 store 层保证 `selectedGroup` 与 `selectedSourceId` 互相清空；服务端若同时收到两者，按 **AND 取交集**（不做报错，保持接口简单）；
   - 「全部书源」= 两者皆空 = 全部已启用书源，永远排在选项卡第一位（用户明确要求保留「搜全部」）。
7. **搜索源数上限只作用于「未显式指定范围」的搜索**：
   - 原逻辑 `sourceIds == null && size > 20 → take(20)` 只针对「全部书源」；
   - 显式选分组与显式给 `sourceIds` 同等对待（整组都跑）。理由：用户选了一个 30 源的分组，只跑 20 个且**没有任何提示**，属于静默少搜，比慢更糟。

---

## 3. 备选方案与否决理由 (Alternatives Considered & Why Rejected)

- **备选方案 A：建 `source_group` 表 + `source_group_ref` 关联表（多对多）**
  - *否决理由*：直接违背工程复杂度惩罚。真实数据里多分组源极少，而多对多会引入分组表的创建/清理/孤儿治理、导入时的分组解析与去重、以及「源被删后空分组怎么办」一整套问题。当前需求（看得见、改得动、搜得到）用一列字符串 + 3 个 SQL 就能满足。
- **备选方案 B：把「未分组」当成一个伪分组存进 `source_group`（值如 `未分组`）**
  - *否决理由*：会与用户真实创建的同名分组冲突；且导入手机备份时会把「未分组」写进源自带字段，污染用户数据。哨兵值只在**查询语义**层存在，不落库。
- **备选方案 C：分组名大小写敏感、改名重名报 409 让用户先处理**
  - *否决理由*：与搜索过滤的 `collate nocase` 语义冲突（列表两组、命中两组），且把清理成本推给用户。合并是更符合直觉的结果。
- **备选方案 D：搜索范围保持「单下拉」，把分组和单源混在同一 `<select>` 里**
  - *否决理由*：需求明确要求「书库页搜索栏下面有分组选项卡，并保留一个『全部书源』选项卡」。选项卡的可见性远好于藏在下拉里：用户一眼能看到自己有哪些分组、每组多少个可用源。
- **备选方案 E：书库页也提供分组的新建 / 改名 / 删除**
  - *否决理由*：职责分离。分组是**书源的组织方式**，属于「书源」页面；书库页只负责「用哪个范围搜书」。两个页面都能改分组会让「我在哪改的」变得难以回答。

---

## 4. 后果与权衡 (Consequences & Trade-offs)

- **正面收益**：
  - 零 schema 变更、零迁移：既有库里的 `source_group` 立刻可用；
  - 备份导入的书源分组**天然生效**（同一个字段），无需为「导入分组」单独写一条链路；
  - 搜索范围收窄是纯 SQL 条件，不引入任何新的执行路径（仍是同一套并发搜索）。
- **负面代价 / 已知限制**：
  - 一个源只能有一个分组，且分组无排序、无颜色；
  - `A,B` 这类多分组字符串被当作一个整体分组名，选择任一子分组都搜不到它（当前真实数据里没有这种源；若将来出现，需要先决定「拆分」还是「整体」，再改 `listSourceGroups` 与过滤条件）；
  - 分组名是「源上的字符串」，因此**删掉最后一个源也就等于删掉了分组**（`listSourceGroups` 自然不再返回它），这与「分组是实体」的心智模型不同，需要在 UI 文案上保持「分组来自书源」的表述。
