# ADR-028: 采用单进程内嵌式双层内容寻址缓存体系 (方案E) 完全整合适配原版漫画规则

## 1. 决策背景 (Context)

为 `legado-server` 引入漫画（图片书源）支持时，面临核心架构与规则兼容挑战：
1. **Legado 原版漫画规则生态极其多样**：
   - Legado Android 原版图片源（`bookSourceType == 2`）不仅通过 HTML `<img>` 标签输出图片，还普遍采用 `<js>` / `@js:` 混淆脚本直接返回 URL 数组、纯文本换行输出、带有图片级单独请求头扩展（`url,{"headers": {...}}`）、或利用 `nextContentUrl` 将单一章节拆散为多页分别加载。
   - 规则层必须全量适配原版各种形态，否则大量社区精选漫画源将直接失效。
2. **图床防盗链与鉴权壁垒**：许多漫画源严格校验请求头 `Referer` 为源站章节 URL，或需要书源登录 Cookie（`CookieJar`）。纯前端直连（方案 A）大面积失效。
3. **海量图片文件的存储管理**：漫画图片数量大（每章数十张，每部数千张），且彩页、广告页或跨章封面在章节间高度重复。直接按“章节目录”落盘（方案 C）无法去重，且单目录文件过多；仅按单图落盘（方案 B）又丢失了“章节完整原子性”，断网容易半截裂图。
4. **架构边界与复杂度控制**：存在现成独立的 Python 漫画站点（`manga_service`），也有将服务物理拆解为微服务子进程的设想（方案 F）。必须按照 `AGENTS.md` 核心原则，在“资源隔离”与“复杂度惩罚（严禁不必要的胶水层、严禁两套鉴权与业务状态）”之间做精准权衡。

---

## 2. 裁定方案 (Decision)

**裁定采用【方案 E：单进程内嵌式双层内容寻址缓存体系】，并深度对齐 Legado 原版漫画规则全量规范**：

1. **规则层：完全整合适配 Legado 原版漫画规则**：
   - 识别 `bookSourceType == 2` 与书架 `ShelfKind.COMIC` 独立分支。
   - 新增 `RuleRunner.mangaImages()` 取数管道：
     - **全属性图片解析**：优先级提取 `data-original` → `data-src` → `data-lazy-src` → `data-actualsrc` → `src`，支持 `srcset` 最大档位与 Base64 格式。
     - **JS 与 JSON 数组原生支持**：对 `<js>` 脚本求值结果中的数组进行保序展开，避免 Java `toString()` 污染。
     - **URL 扩展 Options 支持**：解析 `url,{"headers": ...}` 格式，保留图片专属请求头。
     - **`nextContentUrl` 多页链式拼接**：自动循环抓取章节内分页，聚合为单一连续章节图片列表（带防环路守卫与 100 页上限）。
     - **绝对路径补全与正则净化**：使用 `URI.resolve()` 补全相对路径，执行 `replaceRegex` 剔除垃圾广告图与 1x1 透明占位符。
2. **统一单进程架构**：
   - 漫画解析与缓存能力完全内嵌在 `legado-server`（端口 8080）中。不引入独立运行的外部 Python 进程，不增加子服务端口与跨进程 RPC，保证单 Docker 容器自包含部署与单 SQLite 数据库权威性。
3. **L1 物理字节内容寻址 (去重底座)**：
   - 服务端代抓：复用 `CoverCache.kt` 的校验经验（gzip 解压兜底、图片魔数校验、单图 5 MiB 限制），携带书源 `User-Agent`、`Referer`、Cookie 以及图片级 options 请求头。
   - 存储路径：采用两级十六进制散列目录 `data/legado-server/images/<hash[0:2]>/<hash>`，彻底避免单目录文件过多引起的系统调用性能瓶颈。
   - 文件落盘严格遵循 `.part` 临时文件 + `ATOMIC_MOVE` 原则，避免写入不全。
   - 缓存 Key 定义：`sha256(source_id + '\n' + 规范化URL)`，避免跨源污染。
4. **L2 章节原子清单 (视图层)**：
   - 章节缓存建立 `manifest` 视图，只记录有序的 `cacheKey` 索引，**绝不物理复制图片字节**。
   - 章节原子性：只有全章所有图片均完成落盘后，才将该章标记为 `ready`，并在目录打绿点（`●`）；若任一图片拉取失败，不生成脏 `manifest`，避免断网时展示裂图。
5. **LRU GC 配额控制**：
   - 后台守护任务根据 `manga_image_cache` 表的 `last_access_at` 进行 LRU 淘汰，默认磁盘上限 2 GiB（支持环境变量覆盖），保护当前在读书籍不被误删。

## 3. 备选方案与否决理由 (Alternatives Considered & Why Rejected)

| 备选方案 | 做法 | 否决 / 不作为终态的核心理由 |
| :--- | :--- | :--- |
| **方案 A：前端直连透传** | 服务端只提取图片 URL，浏览器 `<img src>` 直连图床 | **无法突破防盗链**（403）、无法带书源 Cookie、无法脱机断网阅读。仅可作为 P0 极速验证探针，不可作为产品终态。 |
| **方案 B：纯服务端代理缓存** | 仅按单图内容寻址缓存 | 解决防盗链与去重，但**缺乏章节完整性视图**，离线状态机难以判定“全章是否就绪”，断网阅读易出现后半截裂图。 |
| **方案 C：纯章节归档目录** | 每章建独立目录落盘全部图片 | **无法去重**。跨章节重复引用的彩页/跨页/片头广告重复存储数倍体积；成千上万小目录造成 inode 与磁盘空间浪费。 |
| **方案 D：外置 manga_service** | 将漫画跳到或反代至 Python FastAPI 站点 | **严重违反复杂度惩罚**：<br/>1. `manga_service` 是采集入库模型，**完全不吃 Legado 原版书源规则**；<br/>2. 引入第二套 JWT 鉴权、第二套阅读进度表、第二套书架；<br/>3. 用户体验与数据备份割裂。 |
| **方案 F1：Kotlin 子服务搬走解析** | 独立 Ktor 进程，抽 Gradle `:core` 模块 | 为抽 `:core` 需对 `RuleRunner` 与 `Database` 大幅解耦，涉及大量历史规则兼容补丁，**重构风险极高**且无直接增量价值。 |
| **方案 F2：Python 重写规则引擎** | 用 Python 重写 Legado 规则执行器 | **坚决否决**。Rhino JS 沙箱、选择器、`JavaImporter` 空替身、33+ 兼容 API 凝聚了大量历史血泪补丁，Python 重写会全面踩坑。 |
| **方案 F3：独立图片仓库 ImageVault** | 解析留主服务，仅将图片代抓与落盘拆为内部 8081 子服务 | **技术可行，作为特定备选**：当单机漫画达到几百 GB、且并发大图 IO 明确挤占 TTS 与文本时才建议启用。当前常规场景采用方案 E 更加简单轻量、易维护。 |

## 4. 后果与权衡 (Consequences & Trade-offs)

### 正面收益 (Positive Consequences)
1. **原版漫画生态 100% 深度兼容**：完整支持 HTML 懒加载、JS 脚本解密、URL options 自定义头与 `nextContentUrl` 多页章节合并。
2. **防盗链能力 100% 覆盖**：服务端注入真实上下文头信息及图片级 options，彻底解决 403 裂图。
3. **空间与一致性双赢**：L1 字节去重极大节省磁盘，L2 manifest 确保章节离线原子完整性。
4. **零额外运维开销**：单镜像部署，无跨进程端口监听、无内部密钥配置负担。

### 潜在风险与防御对策 (Risks & Mitigations)
1. **`nextContentUrl` 分页死循环风险**：
   - *对策*：加入 `visitedUrls` 集合防死循环检测，且单章最大连页限制设为 100 页。
2. **大图片抓取对主服务 IO 的竞争**：
   - *对策*：引入独立全局限流信号量（如 `MAX_CONCURRENT_IMAGE_FETCH = 8`，单源限流 2），使用独立的 IO 调度器，严禁阻塞 Rhino 沙箱与 TTS 线程。
3. **磁盘空间无节制增长**：
   - *对策*：内置 `ImageCacheGc`，每次写盘检测或定期触发 LRU 清理，优先淘汰非书架/最久未读图片。
