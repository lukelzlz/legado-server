# ADR-031 · 缓存命名空间 `audio`/`comic`/`images`/`covers`，文件名 = 名称 + 20 位短哈希 + 真实扩展名，v2 清掉重下 / v3 只移动

- **状态**：Accepted
- **关联**：[PROPOSAL-031](../proposals/PROPOSAL-031-browsable-cache-layout-and-readable-cover-names.md) · [ACCEPT-031](../acceptance/ACCEPT-031-cache-layout-and-cover-names.md) · [SESSION-049](../sessions/SESSION-049-cache-layout-i18n-and-reader-toc-batch.md)
- **实现**：`server/src/main/kotlin/io/legado/server/AtomicFileStore.kt`（布局与迁移的唯一入口）·
  `ServerConfig.kt`（四个根目录常量）· `CoverCache.kt`（封面命名与定位）· `Database.kt`（`cover_cache.file_path`）
- **提交**：`0fb31ec`（v2）→ `eeef50a`（v3）

---

## 1. 背景

漫画（`ImageCache`）与有声书（`AudioCache`）的字节缓存原本是**内容/URL 寻址的散列分片**：
`images/<hash[0:2]>/<hash>`，封面是 `covers/<sha256 key>`。这对机器友好，但对**人**极不友好：
用户想手工看一眼、备份或清理缓存时，面对的是无法与书对应的 64 位 hex；
封面**连扩展名都没有**，操作系统认不出是什么格式。

用户明确提出（原话）：

> 「优化缓存目录的结构，音频和漫画目录下新建文件夹，名字是书籍的名字，下面再分每个章节的文件夹，
> 音频和图片以实际的格式存在文件夹里，方便我本地查看」
>
> 「不要 8 位章节序号、章节目录 = 章节名+20 位哈希、读取默认只读哈希和序号（**防止中文干扰**）、
> 哈希可以长一些、书名相同时靠哈希区分」
>
> 「把 `images` 目录改成 `comic`，`images` 留着用来放小说插图，封面图也改成有后缀名的形式，
> 名字用小说名字+哈希」

需要裁定四件事：

1. 四个根目录（漫画 / 插图 / 音频 / 封面）叫什么、语义边界在哪；
2. 目录名与文件名的形态，以及**读取到底依赖什么**；
3. 哈希用什么算、多长、能否当唯一标识；
4. 老布局怎么升级 —— 什么时候可以"清掉重下"，什么时候必须"移动"。

---

## 2. 决策

### 2.1 四个命名空间，各归其位

| 根目录 | 常量 | 语义 | 本轮是否写入 |
| :--- | :--- | :--- | :--- |
| `<data>/comic` | `ServerConfig.COMIC_DIR_NAME = "comic"` | 漫画图片字节（L1 唯一副本） | ✅ 写入 |
| `<data>/images` | `ServerConfig.ILLUSTRATION_DIR_NAME = "images"` | **小说插图（预留）** | ❌ 只保证目录存在 |
| `<data>/audio` | `"audio"`（字面量） | 有声书音频字节 | ✅ 写入 |
| `<data>/covers` | `ServerConfig.COVER_DIR_NAME = "covers"` | 书籍封面 | ✅ 写入 |

**为什么插图必须与漫画分开**：漫画缓存的读取定位是「扫目录名里的 `(书哈希)` / `(章节哈希)`」
（见 §2.3），插图若混进同一个根，**两套语义会互相扫到**。
插图根**每次启动都保证存在**（与版本无关的 `Files.createDirectories`），但**不写任何文件**；
写入实现留给后续改动。

> 这解释了「`images/` 是空的」：它不是坏掉的目录，而是**预留根**。

### 2.2 文件名 = 名称 + 20 位短哈希 + 真实扩展名

```
audio|comic/<清洗书名 (20位书哈希)>/<清洗章节名 (20位章节哈希)>/<8位分段号>.<真实扩展名>
covers/<清洗书名 (20位书哈希)>.<真实扩展名>
```

- `书哈希 = sha256(sourceId + "\n" + bookUrl)` 前 **20** 位小写 hex；
- `章节哈希 = sha256(sourceId + "\n" + bookUrl + "\n" + chapterUrl)` 前 **20** 位；
- 分段号 = `%08d`（`CACHE_SEGMENT_INDEX_WIDTH = 8`）；
- 扩展名由 `content_type` 映射（`image/jpeg→jpg` / `audio/mpeg→mp3` / `image/svg+xml→svg`…），
  **未知一律 `bin`，绝不猜**（猜错就是"文件打不开"）；
- 名称部分过 `cacheSafeName()`：控制字符与 `\ / : * ? " < > |` → `_`、空白折叠、
  去尾点与空格、截断（书 60 / 章标题 40）、空则 `未命名`、Windows 保留设备名追加 `_`。

**把 `sourceId` 也算进哈希**：与本仓库既有的缓存 key 约定同源
（`ImageCache.urlHash` / `AudioCache.cacheKey` 都是 `sha256(sourceId + '\n' + url)`）——
不同书源指向同一个 `bookUrl` 时**不串味**（同一本书在两个源上的章节/图片完全可能不一样）。

**为什么哈希要 20 位（80 bit）**：几万本书的碰撞概率可忽略，而目录名仍然短得能一眼看全。

### 2.3 读取**只按哈希**（中文与扩展名都不参与）

`AtomicFileStore.findByNameFree(bookHash, chapterHash, segmentIndex)`：

1. 根目录下找**目录名以 `(bookHash)` 结尾**的书目录；
2. 其中找**目录名以 `(chapterHash)` 结尾**的章节目录；
3. 其中找**文件名以 `00000001.` 开头**的常规文件（扩展名不参与匹配）。

匹配模式只由**已校验的 hex 与数字**拼成。封面同理：`findFlatByNameFree(hash)` 找
**文件名词干以 `(hash)` 结尾**的常规文件。

三级定位顺序：

| 级别 | 依据 | 说明 |
| :--- | :--- | :--- |
| 1 | `file_path`（数据库列） | **快路径**，命中即用 |
| 2 | `findByNameFree` / `findFlatByNameFree` | **无中文实扫**，命中即**回填 `file_path`**（下次回到快路径） |
| 3 | `covers/<key>` 旧形态 | 封面专用兜底（迁移时"对不上书架"的孤儿封面留在这一档） |

**都 miss ⇒ 判缺失、重下，绝不返回错文件。**

⇒ **中文段名/书名只是"给人看的装饰"**：用户手工改名、乱码、书改名、上游改标扩展名
都不会让已缓存的文件失联。**反过来，哈希标记没了就判"不存在"** ——
宁重下，绝不瞎猜一个文件塞给用户。

### 2.4 章节目录因哈希而**天生单射** ⇒ 刻意删除冲突兜底

章节名是**用户数据**：可能重复（"上"/"下"）、可能缺失、可能被改。一旦拿它当**目录唯一标识**，
两章就会互相覆盖，而症状是「某些章节的图/音频变成别人的」这种极难归因的故障。
加哈希后章节目录名单射 ⇒ **不需要任何"冲突了怎么办"的兜底代码**。

**刻意不做碰撞后缀去重**（`(hash-2)` 这类）：读取只认「哈希 + 章节序号 + 分段序号」这三段，
**后缀不参与读取依据**。也就是说一旦两个短哈希撞上，加后缀根本救不了 ——
读的时候谁也不知道该找 `-2` 还是原样，两本书的缓存会互相串味。
**正解只有一个：让哈希足够长**，把碰撞概率压到工程上可忽略。

### 2.5 `cache_layout`：v2 = 清掉重下、v3 = **只移动不清理**

版本存 `app_setting.cache_layout`（`CACHE_LAYOUT_KEY`），当前 `CACHE_LAYOUT_VERSION = "v3"`：

| 读到的版本 | 动作 | 依据 |
| :--- | :--- | :--- |
| `"v3"` | **no-op**（不扫盘、不查库） | 已是最新 |
| `"v2"` | **移动**：`images/` 现存文件搬到 `comic/` + 全部封面改名一次，写回 `v3` | 布局本身没变（还是「书/章可读目录 + 8 位分段号」，读取只认两个哈希与序号），**变的只有根目录名** ⇒ 用户数据零损失，**没有任何理由重下** |
| `v1` / 未设置 | **清掉重下**：`purgeAll()` 三个根 + 删 `manga_image`/`audio` 行 + 封面改名，写回 `v3` | 散列两级目录与新语义**不兼容**（旧文件躺在旧根 `images/` 里，也就是现在的插图预留根） |

**"清掉重下"是针对 v1 散列布局的，别张冠李戴到 v2 上** —— 这是本 ADR 最容易被后来者搞错的一条。

### 2.6 迁移的三条铁律：幂等 / 同名不覆盖 / 失败不阻断

- **幂等**：v3 状态下调用立刻返回 `false`（不扫盘）；`purgeAll()` 第二次调用一定是
  `PurgeResult(0, 0)`；
- **同名不覆盖**：`moveCacheRoot` 与 `migrateCoverFileNames` 在目标已存在同名文件时
  **跳过并计数**（`Files.move` 刻意**不给** `REPLACE_EXISTING`）——
  宁可少移一个，也不能拿半路的字节盖掉用户已有的缓存；封面改名时**不删原件**；
- **失败不阻断**：单文件异常由 `runCatching` 记日志并计数，**绝不抛错**；
  缓存迁移不允许阻断启动。
- `moveCacheRoot` 对每个目标路径都做 `target.startsWith(normalizedTarget)` 越界校验，
  越界计入 `failed` 并跳过。

返回 `MoveResult(files, bytes, skipped, failed)` 与
`CoverMigrationResult(renamed, skipped, failed)`，日志口径：

```
缓存目录结构升级到 v3：漫画根 images -> comic (移动文件=49, 字节=12777092, 跳过=0, 失败=0)
封面改名(改名=196, 跳过=0, 失败=0)
```

### 2.7 封面命名与「同一本书两版封面」的已知边界

`书名 (书哈希).扩展名` **容不下同一本书的两版封面**（换图 / 深度回源补抓）。
处理方式是「**最后写入者拥有这个名字**」：`writeCover` 覆盖同名文件前，
先把**别的 key** 记的路径（进程内与库里的都）清掉（`coverFilePathHolders` → `clearCoverFilePath`）
⇒ 旧 key 只会得到"没有缓存"（回源重下），**绝不直出另一版的字节**。

**孤儿封面**（`cover_cache` 有行但无书架条目引用）**留在原处**，写进代码注释的理由：
① 它没有书身份（既无 `sourceId` 也无 `bookUrl`），"书哈希"在数学上就算不出来；
② 它本来就以 `<key>` 命名，而读取侧的最后一档兜底**正是** `covers/<key>` ⇒ 留原处零损失。

**没有书身份**时（刚上传还没关联、搜索页的书）文件名为 `未命名 (<64位内容 key>).<ext>`：
哈希段就是 key 本身，而 key 在读取时**一定有**（它就是接口路径里那一段）⇒ 天然可定位。
关联的那一刻（`PUT /api/bookshelf/info` 带 `coverKey`）用 `CoverCache.adopt()` **归位**改名。

### 2.8 明确**不改**的东西

`GET /api/images/{key}`、`/api/books/images/...`、`/api/covers/{key}` 等 **API 表面**是
接口/UI 契约，**不是缓存根**。本轮一个字节都不动。

## 3. 备选方案与否决理由

| 备选 | 否决理由 |
| :--- | :--- |
| 保持散列分片（`<hash[0:2]>/<hash>`），只靠 UI 展示书名 | 直接违背用户诉求（"方便我本地查看"）；用户手工清理/备份时仍然面对不可读的文件名 |
| 用「8 位章节序号」当章节目录标识 | 序号是**展示属性**而非身份：它默认 0、可能重复、跨换源/重排会漂移 ⇒ 两章互相覆盖，症状是"某些章变成别人的"，极难归因 |
| 只用章节名当目录名，同名时加 `-2` 后缀 | 后缀**不参与读取依据**（读取只认哈希+序号），加了也救不了串味；正解是让标识本身唯一 |
| 哈希取 8 位（32 bit） | 几万本书/几十万章的量级下碰撞已不可忽略，而碰撞的后果是**静默错字节**（比报错危险得多） |
| 让中文参与读取（按书名找目录） | 用户明确要求"**防止中文干扰**"；且书改名、换源、编码差异都会让中文段漂移，读取会大面积失联 |
| 未知 `content_type` 猜一个扩展名（如默认 jpg） | 文件名说谎正是这套命名要消灭的东西；`bin` 是诚实的 |
| v2 → v3 也"清掉重下"（省事） | 纯粹让用户白白重下几十 GB；v3 只改根目录名，移动是零风险且用户零损失的 |
| v1 → v3 也"移动" | v1 是**两级散列分片**，目录里没有任何 `(哈希)` 标记 ⇒ 移动过来的文件**读不到**（等于留一堆垃圾），语义不兼容只能重下 |
| 迁移失败时抛错中止启动 | 缓存迁移失败不该让整个服务起不来；记日志 + 计数即可（一致性由"读不到就重下"兜底） |

## 4. 影响

**正面**：

- 缓存目录**人能读懂**：哪个书、哪一章、什么格式一目了然；封面有扩展名，系统双击即开；
- 读取**不再依赖任何用户可改的字符串**（中文、扩展名都不参与），手工整理目录不会弄坏缓存；
- 身份**单射** ⇒ 消灭了一整类"错字节"故障的可能性，也顺带删掉了冲突兜底代码；
- `images/` 从漫画手里让出来，为小说插图留好了**互不干扰**的位置。

**代价 / 已知限制**：

- **读取要扫目录**（无中文定位靠 `startsWith`/`endsWith` 匹配目录名）。用进程内缓存
  （`bookDirCache` / `chapterDirCache` / `flatFileCache`）兜住热点；缓存命中前会先验在不在盘上，
  名不对就丢掉重扫 ⇒ 目录被手工改名/删除后能自愈；
- **同一本书容不下两版封面**（§2.7），换图后旧版靠"回源重下"找回，不会直出旧字节；
- 孤儿封面留在 `covers/<key>` 旧形态，**不做清理**（数学上无法改名，且读取侧正需要这一档兜底）；
- 名称段参与**写入**路径长度：书 60 / 章节标题 40 字符截断 + 哈希段，路径总长可控；
- **插图写入链路尚未实现**（`images/` 目前恒为空）。

  `file_path` 指歪**靠哈希兜底** / `GET /api/covers/{key}` 路由级 200 出图 /
