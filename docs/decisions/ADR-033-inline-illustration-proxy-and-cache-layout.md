# ADR-033 · 正文插图必须走服务端代理；缓存沿用 comic 的哈希命名但与 comic 分根

- **状态**：Accepted（本地实现 + 单测 + 真实接口实测；待用户验收）
- **日期**：2026-10-17
- **关联**：[PROPOSAL-034](../proposals/PROPOSAL-034-novel-inline-illustrations.md) · [ACCEPT-033](../acceptance/ACCEPT-033-inline-illustrations.md) · [ADR-028](ADR-028-embedded-content-addressed-manga-cache.md)（漫画缓存体系） · [ADR-031](ADR-031-cache-namespace-comic-images-covers-and-move-only-migration.md)（`images/` = 小说插图预留根）

---

## 1. 背景

连载小说的正文里本来就有插图（`<img>`），但本项目的正文清洗把标签全剥光，
所以"插图功能"的第一件事不是渲染，而是**先让插图在正文里活下来**。

活下来之后立刻面对三个必须拍板的问题：

1. `<img src>` 指向**哪里**？（上游直连 / 本地代理 / 内联 data URL）
2. 落盘**放哪、叫什么**？
3. 和已有的漫画图片缓存（`comic/` + `manga_image_cache`）**共用还是分开**？

---

## 2. 决策

### 2.1 浏览器**永远不直连上游**，一律走 `GET /api/books/images/illustration`

这是**唯一**能让四条需求同时成立的做法：

| 直连上游会怎样 | 后果 |
| :--- | :--- |
| 缺章节页 `Referer` / 书源 Cookie | **图床防盗链 ⇒ 整章裂图**，且没有任何报错（浏览器只画一个裂图图标） |
| 断网 / 图床挂了 | **离线读不到图**（本次需求明确要"能离线看"） |
| 每个用户的浏览器直接请求几十个第三方图床 | 把**用户 IP / UA / 来源页**泄露给这些站点 |
| 上游对 `.jpg` 也返回 `Content-Encoding: gzip` | 浏览器直接解析坏字节 ⇒ 空白图（`SESSION-027` 的封面事故同源） |
| 没有魔数校验 | HTML 错误页会被当成图片缓存下来，症状是"图永远裂且服务端一切正常" |

反向的好处也很直接：**抓取只做一次并落盘**，之后所有客户端共享同一份字节；
`Referer`/Cookie/限流/解压/魔数校验/体积上限全部落在服务端**唯一收口**（`MangaImageFetcher`）。

**为什么不接受 `data:` 内联**：服务端拿不到可校验的字节（无法判魔数/体积），
而正文缓存列、JSON 响应、前端 DOM 都会被一张图的 base64 撑爆；`data:` 还是经典 XSS 载体。
所以清洗阶段 `data:` 一律丢弃（见 PROPOSAL-034 §5.1）。

### 2.2 落盘命名**沿用 comic 的 v3 口径**（`images/<书名 (20位书哈希)>/<章节名 (20位章节哈希)>/<8位序号>.<真实扩展名>`）

理由不是"抄一个现成的"，而是**让三条既有不变量继续成立**：

1. **可浏览**：用户打开 `images/` 能一眼看出"哪本书、哪一章、什么格式"（用户对缓存目录的原始要求）；
2. **可修复**：读取只认 `sha256(sourceId+"\n"+bookUrl)[:20]`、
   `sha256(sourceId+"\n"+bookUrl+"\n"+chapterUrl)[:20]`、8 位序号（`AtomicFileStore.findByNameFree`）
   ⇒ 中文名被改、扩展名被上游改标都不影响命中；`file_path` 只是快路径，失效自动按哈希兜底并回填；
3. **不会串味**：两个短哈希让"书"与"章"都是单射 ⇒ 不需要任何"冲突兜底"，
   也不可能取出兄弟章节的文件。哈希标记被人为删掉则**判缺失并重下**，绝不瞎猜一个文件塞给用户。

**键的口径与漫画/音频完全一致**（`sha256(sourceId + "\n" + url)`，含 `sourceId`）⇒
不同书源指向同一图床地址时不会跨源脏命中（水印/线路不同的图混用极难排查）。

### 2.3 `images/` 与 `comic/` **分开**，并且**不复用** `manga_image_cache` 表

| 维度 | 漫画（`comic/` + `manga_image_cache`） | 小说插图（`images/` + `illustration_cache`） |
| :--- | :--- | :--- |
| 一份清单 | `manga_chapter_cache.images_json`（整章就是这些图） | **正文 HTML 本身**就是清单 |
| 序号的来源 | 清单里的数组下标 | 正文里 `<img>` 的出现顺序 |
| 就绪度 | 整章 `ready/partial`（目录绿点 `●` 的判据） | 没有"整章就绪"概念（缺图只是缺图） |
| 前端入口 | `POST /books/images/manifest` → `GET /api/images/{key}` | `GET /books/images/illustration?…&url=…`（url 由正文给出） |
| 清缓存 | 按书清 + 滑窗 GC + 免死金牌 | 只按书清（跟随"清除缓存（服务器）"） |

把两套语义塞进一张表的代价是**双向污染**：漫画侧任何字段口径调整（例如把 `segment_index`
改成"按字节去重后的序号"）都会静默改变插图的行为，反之亦然。
而分开的成本只有一个 13 列的小表 —— 这笔交易明显划算。

**根目录分开还有一条硬理由**：`AtomicFileStore.findByNameFree` 的定位是"扫目录名里以 `(哈希)` 结尾的目录"。
两套缓存若共用一个根，就会出现**同一本书/同一章在两个语义下互相扫到对方的文件**，
症状是"图放出来是别人的"这种最难归因的故障。

## 3. 后果（Consequences）

**正面**
- 一张图只抓一次；断网可读；客户端零直连；上游错误页/超大文件/伪 gzip 全部在服务端被拦掉。
- 落盘结构对用户可读，且与漫画/音频/封面四套命名空间互不干扰。
- 清缓存（服务器）时会一并回收该书的插图行与孤儿文件（先表后盘）。

**负面 / 已知边界**
- `images/` **没有配额与 GC**：长读大量图文书的部署需要人工关注目录体积（后续可复用漫画的滑窗 GC 思路）。
- 单图上限沿用 `ImageBytes.MAX_BYTES` = **5 MiB**（比需求的"如 8MB"更保守，与封面/漫画同一常量）；
  超过即 502，不落盘。
- 单章离线预热带 **20 张** 上限，超出的图仍需在线时按需下载后才进缓存。
- **老缓存正文的插图找不回来**：改动前 `raw_content` 里的 `<img>` 已被删，属于不可逆信息丢失。
- 抓取失败的插图**不写 `failed` 行**（每次渲染都会重试一次）——
  换来的是"上游恢复后自动好"，代价是持续裂图时会重复请求（前端已做失败占位）。

## 4. 备选方案与否决理由

| 备选 | 否决理由 |
| :--- | :--- |
| 前端直连上游（最简单） | 防盗链必裂图、离线无图、泄露用户 IP —— 与需求正面冲突 |
| 清洗时保留 `data:` 内联图 | 不可校验、可撑爆缓存/响应、XSS 载体 |
| 复用 `manga_image_cache` 单表 | 两套序号语义互相污染（见 §2.3） |
| 按 `sha256(字节)` 内容寻址落盘（像封面那样） | 文件名变成不可读哈希，且"章节内第几张"这一信息丢失（用户明确要"方便本地查看"） |
| 用"8 位章节序号 + 8 位图片序号"当身份 | 章节序号会因换源/重排漂移，两章互相覆盖 ⇒ 错图（AGENTS.md 部落知识明确禁止用展示属性当身份） |
| 每章另建"插图清单接口" | 正文本体已经是清单，多一个接口就多一处需要同步的状态 |
