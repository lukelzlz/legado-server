# ADR-034: 采用服务端候选查询与并集范围模型支持大规模书源搜索选择

## 1. 决策背景（Context）

当书源数量达到 10,000 条时，现有单个 `<select>` 不适合定位书源；把全部书源加载到浏览器再筛选还会造成较大的网络、内存和 DOM 压力。同时用户需要把多个分组与多个单独书源组合成一次搜索范围。

本次需要确定：

1. 书源候选是否由前端全量加载；
2. 多个分组和单独书源同时选择时采用交集还是并集；
3. 是否引入第三方虚拟列表组件；
4. 搜索协议如何表达多个分组。

## 2. 裁定方案（Decision）

### 2.1 候选书源采用服务端查询，且不设置固定条数上限

新增轻量候选查询接口，按关键词和分组查询书源。服务端不设置固定的候选条数上限，前端完整加载当前查询返回的结果。

理由：

- 搜索候选由用户的查询条件决定，不因预设条数上限漏掉匹配书源；
- SQLite 可以直接完成名称、URL、分组过滤；
- 选择结果只保存 ID 与少量展示信息；
- 不影响现有书源管理接口。

### 2.2 多分组与多书源采用并集语义

选择范围定义为：

```text
enabledSources(groups) ∪ enabledSources(sourceIds)
```

结果按书源 ID 去重。

理由：用户表达的是“搜索这些分组，再额外搜索这些书源”。如果采用交集，额外选择的组外书源会被静默排除，容易造成“明明勾选了但没有搜索”的误解。

### 2.3 搜索协议使用集合字段

`SearchRequest` 使用 `groups: List<String>` 与 `sourceIds: List<String>` 表达范围。HTTP 搜索和 WebSocket 搜索使用同一套解析逻辑；没有任何范围时保持全部已启用书源行为。

### 2.4 不引入第三方虚拟列表

本次不通过固定条数上限解决选择问题。继续使用现有 React 组件、CSS 和测试体系，避免为本次选择器增加新的运行时依赖。

## 3. 备选方案与否决理由（Alternatives Considered & Why Rejected）

- **方案 A：前端一次性加载全部书源后本地筛选**
  - *否决理由*：书源初始数据和搜索状态与管理列表强耦合；本提案采用服务端按关键词和分组查询，但不截断查询结果。

- **方案 B：仅把单个 `<select>` 改成可搜索下拉框**
  - *否决理由*：只能改善定位，不能支持多个分组与多个书源组合，也无法彻底解决全量加载问题。

- **方案 C：引入第三方虚拟列表并截断候选结果**
  - *否决理由*：固定截断会隐藏用户实际要找的书源；本次不以条数上限作为交互约束。

- **方案 D：分组与书源取交集**
  - *否决理由*：不符合“多个分组 + 额外书源”的直觉，容易静默漏搜。

- **方案 E：为每个选择范围建立持久化服务端配置**
  - *否决理由*：本次只解决一次搜索的选择体验，引入保存、同步和冲突语义会扩大范围。

## 4. 后果与权衡（Consequences & Trade-offs）

### 正面收益

- 10,000 条书源下仍可通过关键词快速定位，且不会因固定条数上限漏掉匹配项；
- 多分组、多书源混合搜索语义明确；
- 前端候选列表由用户查询条件控制，不额外截断匹配结果；
- 不引入新依赖，不改变书源存储模型；
- HTTP 与 WebSocket 搜索范围保持一致。

### 负面代价

- 选择器需要维护服务端查询和请求取消状态；
- 查询条件过宽时返回体和前端渲染量可能较大，需要依赖用户输入关键词或分组缩小结果；
- 查询条件过宽时需要承受较大的响应体和候选列表，前端仍需保留跨查询的已选状态；
- 多选范围会改变现有单分组搜索请求字段，需要同步更新服务端、前端和契约测试。
