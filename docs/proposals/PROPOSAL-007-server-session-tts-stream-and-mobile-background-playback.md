# PROPOSAL-007: 服务端会话级连续 TTS 音频流与移动端后台稳定播放

## 1. 业务背景与问题痛点

当前在线 TTS 播放器按句调用 `/api/tts/speak`。服务端虽然代理了 Edge-TTS 与自定义 HTTP TTS，但每次请求仍要先完整收集一段音频，再返回一个 Blob；前端还要在句子结束时切换下一个 Blob。桌面端可以依靠预取维持体验，但移动端进入后台后，频繁的 Fetch、Blob URL 切换和短请求容易被浏览器限速、挂起或回收，造成断音、无法跨章或锁屏播放不稳定。

本提案只调整在线 TTS 的传输与合成编排方式：客户端仍使用现有句子切分、段落/句子高亮、播放控制、睡眠定时和跨章状态机；服务端负责维护一次朗读会话的待合成队列，将 Edge-TTS 或自定义 HTTP TTS 的结果按顺序汇入一条可持续播放的 MP3 音频流。

## 2. 目标与非目标 (Goals & Non-Goals)

### Goals (目标)

1. 一次在线 TTS 朗读会话只建立一条浏览器音频流，正常跨句、跨段落、跨章节持续输出，不再为每句创建新的 Blob 播放源。
2. 保留现有客户端体验：句子/段落切分、高亮与视口跟随、播放/暂停、上一句/下一句、点击段落定位、睡眠定时、MediaSession 和自动跨章连播均保持现有语义。
3. 将 Edge-TTS 与自定义 HTTP TTS 的上游请求编排移入服务端。服务端按队列顺序合成并尽快转发音频，不等待整章或整场会话完成后才开始播放。
4. 通过独立的轻量进度元数据通道报告当前会话、章节、段落和句子边界，使连续音频流不损失现有高亮定位能力。
5. 在 Android Chrome、iOS Safari/PWA 的用户手势启动播放后，屏幕锁定或页面进入后台时尽量保持单条音频流和 MediaSession 播放连续。
6. 支持暂停/继续、跳句、点击段落和上一句/下一句：暂停时停止服务端继续取上游，定位操作从目标句重建音频流并同步高亮状态。
7. 服务端会话只保存在内存中。停止、断开、超时或异常后取消上游请求并释放队列、连接和缓存引用。

### Non-Goals (非目标)

1. 不改变现有文本净化、句子切分、阅读进度落盘和可见播放控制的产品逻辑。
2. 不把整章预先合成为完整音频文件，不新增音频文件持久化、下载任务或 SQLite 表。
3. 不引入 ffmpeg.wasm、服务端音频转码服务或重量级客户端音频解码器。连续流要求上游输出可直接拼接的 MP3 音频帧。
4. 自定义 HTTP TTS 不承诺支持任意格式；非 `audio/mpeg` 或无法直接拼接的响应应明确失败，不静默转换。
5. 不保证用户强制关闭浏览器、杀掉 PWA、系统回收页面或系统完全断网后仍能持续播放。
6. 不扩展微信内置浏览器、Android WebView 等未确认的容器环境；本次移动端验收范围为 Android Chrome 与 iOS Safari/PWA。
7. 不保留旧的“每句独立 Blob 播放”作为长期并行回退链路；协议切换完成后，在线 TTS 使用新的会话流模型。

## 3. 核心用户故事 (User Stories)

### Story 1: 在线 TTS 低中断连续播放

- **场景**：作为读者，我在阅读器中选择 Edge-TTS 或自定义 HTTP TTS 并点击“朗读”。
- **行为**：客户端沿用当前句子切分和播放状态机，服务端建立一个朗读会话；音频元素绑定会话音频地址后，服务端按队列合成并持续写入 MP3 数据。下一句不再触发新的浏览器音频请求，读者听到的内容顺序和当前体验一致。
- **结果**：首个有效音频片段准备好后即可开始播放，后续句子由服务端连续衔接；服务端不必等待整章完成。

### Story 2: 移动端后台和锁屏听书

- **场景**：作为 Android Chrome 或 iOS Safari/PWA 用户，我在前台通过用户手势开始朗读，然后锁屏或切到后台。
- **行为**：浏览器继续使用同一条原生音频流，MediaSession 保留书名、章节名和控制动作；服务端继续处理已入队内容，并按需接收后续队列请求。
- **结果**：在浏览器和系统没有强制挂起网络/媒体任务的情况下，句子之间不因 Blob 切换产生额外请求断点；锁屏暂停/继续状态与阅读器一致。

### Story 3: 跨章节持续队列

- **场景**：作为开启自动连播的读者，我听完当前章节最后一句。
- **行为**：客户端按原有逻辑保存进度、加载下一章正文并把新的句子队列追加到同一个在线 TTS 会话；服务端在现有队列消费完后继续输出下一章音频，进度元数据切换到新章节。
- **结果**：正常跨章不更换音频元素或音频流；章节切换时高亮、滚动/翻页和阅读进度仍按现有逻辑工作。

### Story 4: 暂停、定位与控制操作

- **场景**：作为朗读中的读者，我点击暂停、下一句，或点击正文中的某个段落。
- **行为**：暂停只暂停播放并阻止服务端继续拉取新的上游片段；下一句、上一句和段落点击取消当前会话的未完成合成，从目标 chunk 重建会话流，并通过元数据重新建立高亮基线。
- **结果**：控制器显示正确的 `buffering/playing/paused` 状态，不播放旧队列内容，不因异步回调重新触发已取消的句子。

### Story 5: Edge-TTS 与自定义 HTTP TTS 一致接入

- **场景**：作为读者，我切换 Edge 发音人、语速/语调，或使用已配置的自定义 HTTP TTS。
- **行为**：客户端仍提交现有的文本、发音人、语速、语调和自定义请求参数；服务端分别调用对应上游，并将兼容的 MP3 片段按队列顺序写入同一会话流。
- **结果**：两类在线引擎共享相同的播放、高亮、暂停和定位体验；上游鉴权信息只由服务端代发，不在浏览器直接请求第三方地址。

### Story 6: 网络中断与上游失败

- **场景**：移动网络切换、服务端上游超时或自定义 TTS 返回错误。
- **行为**：服务端向元数据通道报告可识别的错误并关闭当前流，取消未完成上游任务；客户端保留最近确认的 chunk，在可恢复的音频错误后从该 chunk 重建会话，最多重复当前句，不回放已确认完成的旧句。
- **结果**：不可恢复的错误进入现有暂停/错误提示状态；用户可以继续点击播放或重新定位，不会留下悬挂会话和无限重试。

## 4. 拟定协议与行为边界

### 4.1 会话与请求语义

在线 TTS 仍由客户端按现有 chunk 语义提交文本和播放参数，但请求对象从“立即返回一段 Blob”变为“向会话追加队列项”。建议协议由三类同源请求组成：

- 会话控制请求：创建、追加 chunk、暂停、继续、定位重建、停止；继续使用 JSON 和现有鉴权/CSRF 机制。
- 音频请求：绑定会话的 `GET` 长连接，响应 `audio/mpeg`，服务端以 chunked/HTTP streaming 方式顺序写入可播放 MP3 数据。
- 进度事件请求：绑定会话的 SSE 长连接，报告 chunk 开始、chunk 完成、章节切换、暂停、错误和结束等事件。

音频请求和进度事件请求只允许访问创建者的内存会话。会话 ID 使用不可预测的随机值，停止、超时、认证失效或客户端断开时立即清理。

### 4.2 队列与播放顺序

服务端对单个会话按 chunk 顺序串行调用上游 TTS，限制待处理队列长度和单会话并发，避免移动端反复操作造成上游请求堆积。已发送到音频流的 chunk 不再重复写入；定位和重连通过新的会话代际/游标丢弃旧任务。

Edge-TTS 使用现有 XML 转义、握手版本、随机 `muid`、空文本守卫和超时/abort 保护。自定义 HTTP TTS 继续使用现有模板参数和服务端请求头代理，但必须返回可直接拼接的 MP3；服务端不得把任意音频容器混入连续流。

### 4.3 断线、暂停和重建

- 音频流断开：客户端以最近确认的 chunk 为恢复点重建会话，允许重复当前句一次；恢复失败后停止自动重试并显示现有错误提示。
- SSE 断开：只重连元数据通道并从当前会话游标恢复状态，不能影响已经建立的音频播放。
- 暂停：浏览器暂停原生音频；服务端暂停从队列取新任务，保留未消费队列，继续操作恢复。
- 跳句/点击段落/上一句/下一句：取消旧会话或使其代际失效，按目标 chunk 建立新音频流，禁止旧流和旧回调改变当前 UI。

## 5. 验收基准 (Acceptance Criteria)

- [ ] **协议建立**：在线 TTS 能创建内存会话，并返回音频流地址、进度事件地址和会话游标；所有控制、音频和事件请求均需通过现有登录鉴权。
- [ ] **连续音频**：服务端在首个 chunk 可用时开始发送 `audio/mpeg`，不等待整章；正常连续播放多个 chunk 时浏览器只使用一个音频流，不为每句创建 Blob URL 或新的音频元素。
- [ ] **队列追加**：追加下一句、追加下一章不会中断已有音频流；服务端按客户端 chunk 顺序合成，元数据事件与音频顺序一致。
- [ ] **体验保持**：现有句子/段落高亮、视口跟随、播放/暂停、上一句/下一句、点击段落、睡眠定时、MediaSession 和自动跨章连播测试通过。
- [ ] **定位正确**：跳句或段落点击后旧流被取消，目标句从新流开始播放，旧会话的异步结果不能覆盖当前高亮或触发错误的自动连播。
- [ ] **引擎覆盖**：Edge-TTS 和返回可拼接 MP3 的自定义 HTTP TTS 均能连续输出；非 MP3/不兼容格式返回明确错误并释放资源。
- [ ] **异常清理**：客户端停止、音频断开、SSE 断开、上游超时、认证失效和应用停止后，服务端不残留上游连接、队列任务或会话对象。
- [ ] **移动端验收**：在 Android Chrome、iOS Safari/PWA 中由用户手势启动后锁屏/切后台进行持续朗读测试；允许浏览器或操作系统强制挂起时按已声明的非目标处理。
- [ ] **自动化验证**：新增前端连续流/重连/定位测试，新增后端队列、流式响应、取消清理、Edge/custom 适配测试，并通过 `npm --prefix web run check`、`npx tsx web/test/run-all.ts`、`./gradlew :server:test`。

## 6. 风险与待实现约束

1. 移动浏览器对后台网络、自动播放和锁屏媒体的策略由系统控制；实现必须要求首次播放发生在用户手势中，并把系统强制挂起作为不可保证场景。
2. MP3 片段直接拼接要求自定义 TTS 输出满足协议约束。无转码方案可以控制复杂度和延迟，但会缩小自定义源的格式范围。
3. 三条同源连接的生命周期必须统一管理；任一连接异常都要避免把已取消会话的异步结果写入新会话。
4. 内存会话不写数据库，需设置空闲/最大生命周期和队列上限，并在流关闭时验证资源确实释放。
