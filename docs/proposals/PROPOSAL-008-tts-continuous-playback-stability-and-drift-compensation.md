# PROPOSAL-008: TTS 连续播放稳定性、相对时钟锚定与缓冲弹性架构

## 1. 业务背景与问题痛点

在 PROPOSAL-007 引入服务端会话级音频流与独立事件通道后，移动端与桌面端实现了单条连续流播放。但在用户听书约 2 分钟（连续播放 40~50 个句子）时，播放器会出现静音卡死，界面不再推进；而当用户手动点击正文中的其他句子时，又会重新恢复播放。

经全链路排查，根因为：
1. **服务端绝对时钟与前端硬件时钟累积漂移破限**：服务端 `audioCursorMs` 按 MP3 理论帧长累加，前端 `audio.currentTime` 为硬件时钟。每个短句受 MP3 Priming/Padding 样本与声卡重采样影响产生约 4~6ms 系统偏差。播至 40~50 句时累积漂移超过 180ms，导致 `nowMs + 180 < endMs` 永远为真，`onEnd` 判定永久阻塞进入死锁。
2. **前瞻缓冲深度不足（仅 2 分片）**：网文短句居多（1~2 秒/句），2 分片仅提供 2~3 秒音频缓冲，遇 Edge-TTS 握手抖动极易引发 Buffer Underrun。
3. **缺少音频流停滞（Stall）与断粮唤醒机制**：浏览器 `<audio>` 在流式管道饥饿后可能进入 `stalled` 假死，未配备主动拉活看门狗。

## 2. 目标与非目标 (Goals & Non-Goals)

- **Goals**：
  - 彻底消除跨句累加时钟漂移，改用**单句局部相对时钟（`durationMs`）+ 切句基准动态锚定（Anchor Resync）**，杜绝死锁。
  - 增加**停滞推进看门狗（Stall Watchdog）**：当前分片已播至理论末尾且下一分片已到达时，主动解除等待并推进 `onEnd`。
  - 前瞻预加载窗口从 2 分片扩大至 **5 分片滑动窗口**，保持 15~20 秒安全缓冲水位。
  - 监听 `<audio>` 的 `stalled` 与 `waiting` 事件，流恢复时自动触发 `play()` 拉活。
  - 服务端 Edge-TTS WebSocket 握手增加单次重试机制，抵御突发网络抖动。
- **Non-Goals**：
  - 本次不改动 Web Speech 本地语音合成。
  - 本次不修改书架、书籍正文存储与章节加载逻辑。

## 3. 核心用户故事 (User Stories)

- **Story 1（长时间连播不死锁）**：用户开启 Edge-TTS 或自定义 TTS，连续收听 30 分钟以上（跨越 100+ 个短长混合句子），界面高亮与音频平滑切换，绝不在 2 分钟时卡死。
- **Story 2（短句密集抗抖动）**：当遇到小说中连续单字、单句对话（“好。”、“是的。”、“快走！”）时，由于 5 分片前瞻缓冲，音频播放持续平滑，不发生 Buffer Underrun。
- **Story 3（网络波动自动复苏）**：当网络短暂丢包导致流式音频暂停时，在数据恢复后播放器自动恢复播放，不丢失进度，无需用户手动点选刷新。

## 4. 验收基准 (Acceptance Criteria)

- [ ] 自动化测试覆盖：模拟 60+ 分片时钟偏差，相对时钟锚定机制全部平稳触发 `onEnd`，累积漂移为 0。
- [ ] 服务端单元测试覆盖：`chunk_end` 事件包含 `durationMs` 与 `audioEndMs`，WSS 异常时平稳处理。
- [ ] 本地前后端综合测试套件通过（`npm run check` + `tsx web/test/run-all.ts` + `./gradlew :server:test`）。
