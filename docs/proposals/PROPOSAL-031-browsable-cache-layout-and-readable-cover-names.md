# PROPOSAL-031 · 缓存落盘可浏览化（v2）+ 漫画根 / 封面命名（v3）

- **状态**：Implemented（本地已实现并通过单测；待验收）
- **关联**：[ADR-031](../decisions/ADR-031-cache-namespace-comic-images-covers-and-move-only-migration.md) · [ACCEPT-031](../acceptance/ACCEPT-031-cache-layout-and-cover-names.md) · [SESSION-049](../sessions/SESSION-049-cache-layout-i18n-and-reader-toc-batch.md) · [PROPOSAL-028](PROPOSAL-028-manga-support-and-content-addressed-cache.md)（漫画缓存体系，本提案不改其语义，只改落盘形态） · [PROPOSAL-029](PROPOSAL-029-audiobook-support-and-cache-playback.md)（有声书缓存体系，音频根同样受益）

---

## 1. 需求来源（用户原话）

> 「优化缓存目录的结构，音频和漫画目录下新建文件夹，名字是书籍的名字，下面再分每个章节的文件夹，
> 音频和图片以实际的格式存在文件夹里，方便我本地查看」

随后就细节逐步明确（原话）：

> 「不要 8 位章节序号、章节目录 = 章节名+20 位哈希、读取默认只读哈希和序号（防止中文干扰）、
> 哈希可以长一些、书名相同时靠哈希区分」

v3 追加（原话）：

> 「把 `images` 目录改成 `comic`，`images` 留着用来放小说插图，封面图也改成有后缀名的形式，
> 名字用小说名字+哈希」

---

## 2. 现状与缺口（改动前）

| 环节 | 实际状态 |
| :--- | :--- |
| 漫画图片 | `images/<hash[0:2]>/<hash>` —— **两级散列分片**，用户打开目录只看到一串 64 位 hex，书名/章节名/扩展名全不可见 |
| 音频 | 同为 URL 寻址的散列命名，落盘名与「这是哪本书的哪一章」毫无关系 |
| 封面 | `covers/<sha256 key>` —— **没有扩展名、没有书名**；本地双开图片查看器打不开（不知道是什么格式） |
| 定位 | 完全依赖数据库里的 key/`file_path`；一旦落库路径失效，磁盘上那份文件就**永远找不回来**（只能重下） |
| 小说插图 | **没有预留位置**；漫画占着 `images` 这个"看起来像插图"的目录名 |

核心痛点不是"占盘"，而是**可运维性**：用户想手工看一眼/备份/清理缓存时，
面对的是一堆无法与书对应的哈希目录。

---

## 3. 目标

1. **人能看懂**：`audio|comic/<书名 (20位书哈希)>/<章节名 (20位章节哈希)>/<8位分段号>.<真实扩展名>`，
   漫画/音频/封面三个根目录下的每一项都能一眼看出「哪本书、哪一章、什么格式」。
2. **机器仍能可靠定位**：读取**只认哈希与序号**（中文与扩展名不参与），
   用户手工改中文名、上游改标扩展名都不影响命中。
3. **升级不吃数据**：能安全迁移的一律**移动**，不让用户为一次目录改名重下几十 GB。
4. **命名空间各归其位**：漫画 `comic`、小说插图 `images`（预留）、音频 `audio`、封面 `covers`，
   四套语义不互相扫到。

## 4. Non-Goals

- **不实现插图写入链路**：`images/` 只是**预留根**（启动时保证存在且为空），
  写入留待后续改动（[ADR-031 §2.5](../decisions/ADR-031-cache-namespace-comic-images-covers-and-move-only-migration.md)）。
- **不改任何对外 API 表面**：`GET /api/images/{key}`、`/api/books/images/...`、`/api/covers/{key}`
  是**接口/UI 契约**，不是缓存根 —— 本轮一个字节都不动。
- **不清理旧封面残留**：拿不到书身份的孤儿封面**留在原处**（见 §5.4）。
- **不做碰撞后缀去重**（`(hash-2)` 这类）：读取只认哈希，后缀不参与定位，加了也救不了 ——
  正解是**让哈希足够长**（见 §5.3）。
- **不做"同一本书多版封面"并存**：可读命名天生容不下两版（见 §5.4 的已知边界）。

---

## 5. 方案

### 5.1 v2：可浏览目录（书 → 章 → 分段）

```
<data>/comic/<清洗书名 (20位书哈希)>/<清洗章节名 (20位章节哈希)>/<8位分段号>.<真实扩展名>
<data>/audio/<同上>
```

- 书哈希 = `sha256(sourceId + "\n" + bookUrl)` 前 **20** 位小写 hex；
- 章节哈希 = `sha256(sourceId + "\n" + bookUrl + "\n" + chapterUrl)` 前 **20** 位；
- 分段号 = `%08d`（如 `00000001`）；
- 真实扩展名由 `content_type` 映射（`image/jpeg → jpg`、`audio/mpeg → mp3`、
  `image/svg+xml → svg`…），**认不出来一律 `bin`，绝不猜**。

三个宽度都是**唯一常量**（`BOOK_HASH_LENGTH` / `CHAPTER_HASH_LENGTH` / `CACHE_SEGMENT_INDEX_WIDTH`），
写入与读取两侧引用同一常量，任何地方不得再写字面量。

> 为什么书名/章节名要清洗：AGENTS.md 铁律 —— `Path.resolve()` 对非法字符（书名里的换行、
> `/`、`:`）**会抛异常**，不是返回一个不存在的路径。而本次路径**由用户数据拼出来**，
> 所以拼装一侧必须过 `cacheSafeName()`（控制字符与 `\ / : * ? " < > |` → `_`、空白折叠、
> 去尾点与空格、截断、空则 `未命名`、Windows 保留设备名加 `_`），存储一侧再校验一次
> （拒 `..`、绝对路径、盘符、空字节、反斜杠，并断言 `normalize()` 后仍在根内）。

### 5.2 读取只认哈希（「防止中文干扰」的落地）

`AtomicFileStore.findByNameFree(bookHash, chapterHash, segmentIndex)`：

1. 根目录下找**目录名以 `(bookHash)` 结尾**的书目录；
2. 其中找**目录名以 `(chapterHash)` 结尾**的章节目录；
3. 其中找**文件名以 `00000001.` 开头**的常规文件（扩展名不参与匹配）。

匹配模式只由**已校验的 hex 与数字**拼成 ⇒ 用户把书名目录改成乱码、上游改标 `content_type`
（⇒ 扩展名不同）都照样命中。三级定位顺序对外表现为：

`file_path`（数据库里的快路径） → `findByNameFree(...)`（无中文实扫） → 都 miss ⇒ **判缺失、重下**，
**绝不返回错文件**。

### 5.3 章节目录因哈希而单射 ⇒ 删除冲突兜底

章节名是**用户数据**：可能重复（"上"/"下"）、可能缺失、可能被改。加哈希后章节目录名
**天生单射**，于是**刻意删掉**了"同名冲突怎么办"的兜底代码 —— 同一文件被两章覆盖会**静默错字节**，
而这类错误的症状是「某些章节的图/音频变成别人的」这种极难归因的故障。
正解是让标识本身唯一，而不是撞了再打补丁。同理**不做**碰撞后缀：后缀不参与读取依据。

### 5.4 v3：漫画根改名 + 封面可读命名

```
<data>/comic/...                       ← 原 images/（漫画），改名
<data>/images/                         ← 小说插图**预留**根（空目录，本次不写入）
<data>/covers/<书名 (20位书哈希).<扩展名>
```

封面命名与书/章目录同一口径：哈希段是**读取定位的唯一依据**，书名只是给人看的，
扩展名取真实类型。没有书身份时（刚上传还没关联的封面、搜索页的书）退化为
`未命名 (<64位内容 key>).<ext>` —— 哈希段就是 key 本身，而 key 在读取时**一定有**
（它就是接口路径里那一段）⇒ 天然可定位。

**已知边界（刻意为之）**：`书名 (书哈希).扩展名` 容不下同一本书的两版封面。
处理方式是「最后写入者拥有这个名字」：覆盖时把**原来那把 key** 记的 `file_path` 清掉，
于是旧 key 只会得到"没有缓存"（回源重下），**绝不直出另一版的字节**。

**孤儿封面**（`cover_cache` 有行但没有任何书架条目引用）**留在原处**，两条理由任一条都足以定案：
① 它没有书身份（既无 `sourceId` 也无 `bookUrl`），"书哈希"在数学上就算不出来；
② 它本来就以 `<key>` 命名，而读取侧的**最后一档兜底正是** `covers/<key>` ⇒ 留原处零损失。

### 5.5 迁移：v2 清掉重下、v3 只移动

版本判据是 `app_setting.cache_layout`（`CACHE_LAYOUT_KEY = "cache_layout"`，当前 `CACHE_LAYOUT_VERSION = "v3"`）：

| 读到的版本 | 动作 |
| :--- | :--- |
| `v3` | **no-op**（不扫盘、不查库） |
| `v2` | **移动**：`images/` 下现存文件原样搬到 `comic/`；再对全部封面做一次改名；写回 `v3` |
| `v1` / 未设置 | 散列两级目录与新语义不兼容 ⇒ **清掉重下**（`purgeAll()` + 删 `manga_image`/`audio` 表行），写回 `v3` |

v3 的移动语义（`moveCacheRoot`）：

- 目标已存在同名文件 ⇒ **跳过并计数**（`Files.move` 刻意**不给** `REPLACE_EXISTING`：
  宁可少移一个，也不能拿半路的字节盖掉用户已有的缓存）；
- 单文件失败 ⇒ 记日志计数，**绝不抛错**（缓存迁移不允许阻断启动）；
- 搬空的旧章节目录壳子一并收走，但**保留 `images` 本身**（它就是插图预留根，必须存在且为空）。

封面改名（`migrateCoverFileNames`）同样**只改名不删不改内容**：能对上书架的用书名 + 书哈希，
对不上的留在原处；目标同名已存在 ⇒ 跳过且**不删原件**；单张失败记日志计数。
扩展名以**真实字节**为准（`cover_cache.content_type` 历史上有 `image/*` 这种占位值，
直接拿它映射会得到 `.bin`，而本来是一张好端端的 jpg）。

## 6. User Stories

1. 作为自建服务的使用者，我打开 `data/comic`，**一眼就能找到《让词条飞一会》的第 4 话**，
   里面是 `00000000.jpg`… 这样的连续图片，双击就能看。
2. 作为自建服务的使用者，我打开 `data/covers`，看到的是 `让词条飞一会 (445cd76eb2b4bd301527).jpg`
   —— **有书名、有扩展名**，操作系统能直接认出是图片。
3. 作为已经缓存了几十 GB 的用户，我升级到 v3 后**缓存还在**（`images → comic` 是移动，不是清理），
   服务启动日志明确告诉我移了多少文件、跳过多少、失败多少。
4. 作为手工整理过目录名的用户，我把某本书的中文目录名随手改成别的，**阅读/播放照样命中**
   （读取只认哈希与序号）。
5. 作为运维者，我想知道 `images/` 为什么是空的 —— 文档明确写着它是**小说插图预留根**，
   当前不写入。

---

## 7. 验收要点

见 [ACCEPT-031](../acceptance/ACCEPT-031-cache-layout-and-cover-names.md)。核心可观察行为：

- 目录结构与命名逐字符合 `书名 (20位哈希)` / `章节名 (20位哈希)` / `8位分段号.扩展名`；
- `covers/` 下 **0 个无扩展名文件**；
- 把某本书的中文目录名改成乱码 ⇒ **仍能正常阅读**（哈希定位）；
- 删掉目录名里的 `(哈希)` 标记 ⇒ **判为缺失并重下**（宁重下，绝不瞎猜一个文件塞给用户）；
- v2 → v3 之后 `app_setting.cache_layout = v3`，且 `comic/` 里的文件是**从 `images/` 搬过去的**
  （字节数一致、行数不变，无重下痕迹）。
