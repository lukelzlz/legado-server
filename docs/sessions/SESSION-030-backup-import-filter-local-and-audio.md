# SESSION-030: 备份导入过滤本地图书与音频

## 0. 需求

用户提供 `te/` 目录（含 `bookshelf.json` 434 条真实数据 + `分类判别方法.md` 规范 + `bookshelf-report.md` 清单），
要求**备份导入时过滤掉本地图书和音频**。

## 1. 为什么要过滤

服务端只提供**文本阅读**能力，这两类导入后必然不可用：

| 类别 | 为什么用不了 |
| :--- | :--- |
| **本地图书**（14 条） | `bookUrl` 是手机本机的 `content://`（Android SAF）/ `file://` / `webDav::` 路径，**服务端读不到** ⇒ 章节 0、正文空 |
| **音频/听书**（31 条） | 内容源是 TTS 音频流，服务端只做文本渲染 ⇒ 点开也是空 |

导入它们只会污染书架（表现为一批点不开的死书）。

## 2. 分类规范（来自 `te/分类判别方法.md`）

判定**必须按顺序**，因为本地书没有 `tab` 字段：

1. **先判本地图书** —— 若先判 `tab`，本地书会落进兜底分支被误判为在线小说
2. **再判 `tab`** —— `"听书"` → 音频；`"小说"` → 在线
3. **兜底** —— `tab` 解析失败一律算在线小说

### 本地图书判据（满足任一）

- `bookUrl` 以 `content://` 开头
- `bookUrl` 以 `file://` 开头
- `origin` 以 `webDav::` 开头（坚果云等）
- `origin` 以 `loc_book` 开头（**本服务自己**导入本地书时写的虚拟书源）
- `type == 264`（交叉验证）

### `tab` 提取

在线书源的 `bookUrl` 形如：

```
data:;base64,eyJ...LCJ0YWIiOiLlkKzkuJoifQ==,{"type":"qingtian"}
```

用 `eyJ`（`{"` 的 base64）作锚点抓出 base64 段，解码后取 `tab`。
**任一步失败返回 null，不抛异常** —— 本地书走的就是这条路径，判 null 是正常流程。

## 3. 真实数据核对（434 条）

| 项目 | 规范预期 | 实测 |
| :--- | :--- | :--- |
| 总条数 | 434 | **434** ✅ |
| type 分布 | `{8:374, 24:15, 32:31, 264:14}` | **完全一致** ✅ |
| 本地图书 | 14 | **14** ✅ |
| 音频 | 31 | **31** ✅ |
| 在线小说 | 389 | **389** ✅ |
| **过滤合计** | — | **45** |

**注意**：`374 + 15 = 389`，那条 `tab` 解析失败的兜底记录（type=8）**本身就在这 374 里**，
不是额外新增的一条。我在测试里曾多算 1 条（构造了 435），被自己的用例抓出来并修正。

## 4. 实现

### 新增 `ShelfKind.kt`

纯函数分类器（`enum ShelfKind { ONLINE, LOCAL, AUDIO }`），与规范一一对应：

- `of(bookUrl, origin, type, kind)` —— 按顺序判定
- `isLocalBook(...)` —— 本地图书判据
- `decodeTab(...)` —— base64 载荷取 `tab`，全程 null-safe

抽成独立文件的理由：**判定逻辑与导入流程解耦**，可单独做真实数据核对，
且今后别处（如书源体检、书架清理）若要复用不必复制粘贴。

### `BackupImporter.kt`

`parseShelf` 增加 `kind` 字段；`import()` 里：

```kotlin
val shelf = parsedShelf.filter { it.kind == ShelfKind.ONLINE }
val skippedLocal = parsedShelf.count { it.kind == ShelfKind.LOCAL }
val skippedAudio = parsedShelf.count { it.kind == ShelfKind.AUDIO }
```

**过滤在 `backfillCovers` 之前** —— 否则会白白为 45 本不导入的书抓封面。

### 摘要与前端

`BackupImportSummary` 增加 `skippedLocal` / `skippedAudio`（默认 0，向后兼容），
前端 toast 与确认弹窗如实告知跳过数量：

> 导入完成：书源 62，替换规则 3，书籍 389，阅读进度 388；
> **已跳过 45 条服务端用不了的书（本地图书 14、音频听书 31）**

**为什么不静默跳过**：用户看到「434 条备份只导入 389 本」会以为出 bug 了，
必须给出原因而不是让人自己猜。

## 5. 明确不用的判据（规范里的反面教材）

| ❌ 错误写法 | 为什么错 |
| :--- | :--- |
| 用 `.epub` 扩展名判本地书 | TXT/PDF/MOBI 走**完全相同**的 `content://` + `type:264` 机制，会全部漏判 |
| 用 `type` 单独判类别 | `type` 是 Legado 内部枚举，跨版本会变（同一份数据就有 8/24/32/264） |
| 先判 `tab` 再判本地书 | 本地书无 `tab`，会被挤进兜底分支误判为在线小说 |

## 6. 验证

- `ShelfKindTest`（**13 用例**）：真实样例（webDav / loc_book）、
  协议判定不依赖扩展名、判定顺序（本地优先于 tab）、
  `decodeTab` 对 7 种畸形输入不抛异常、**真实 434 条分布核对**
- 独立 Node 脚本对 `te/bookshelf.json` 跑一遍判定，与规范**逐项一致**
- 回归：302 → **315** 用例，失败 **54 → 54 集合逐条一致** ⇒ 零回归
- 前端：`npm run check` 0 错误、`tsx run-all.ts` **146/146**

## 7. 沉淀的教训

1. **过滤类需求的判据要来自数据而非直觉**：用户给的 `te/分类判别方法.md` 是
   从真实 434 条归纳的规范（含反面教材），直接照做比自己猜字段可靠得多。
2. **判定顺序是逻辑的一部分**：本地书缺 `tab` 字段，顺序反了不会报错、
   只会静默误判 —— 这类 bug 极难通过观察发现，必须用测试锁定顺序。
3. **静默过滤要报告**：少导入 45 本条不说明，用户会当成 bug。
4. **抽成纯函数才好核对**：把判定从导入流程里抽出来后，才能拿全量真实数据跑比对。
