# 历史推演归档：开书延迟、正文离线缓存吞吐与目录性能重构

## 1. 历史问题现象与排查背景
- **问题现象**：在 Web 客户端打开多章节小说或执行全书搜索时，界面出现明显卡顿，开书首次请求耗时过长，目录滚动掉帧。
- **排查背景**：Legado 原生 Android 客户端依赖本地 SQLite 与内存常驻，而在 Web/服务端架构下，如果每次开书均全量拉取远程目录并串行解析规则，会导致极高的首屏延迟与网络瓶颈。

## 2. 曾尝试的无效路径与失败原因
1. **无效路径 1：前端每次进入阅读器均通过服务端 API 实时解析全部目录**
   - *失败原因*：对于几千章的长篇小说，Jsoup/JsonPath 规则解析与全量 JSON 序列化在网络传输上耗时超过 3~5 秒，阻塞了首章正文渲染。
2. **无效路径 2：服务端在搜索阶段并发全量抓取各书源的目录与正文**
   - *失败原因*：大量并发外部网络请求引发目标站点限流（403/429）或连接超时，拖垮服务端并发工作线程池。
3. **无效路径 3：前端使用原生 DOM 渲染数千个目录项**
   - *失败原因*：DOM 节点过多导致页面重绘与重排极其缓慢，内存占用暴增。

## 3. 最终落地的解决策略
1. **目录按需加载与虚拟化滚动（Virtualized TOC）**：
   - 前端采用虚拟列表仅渲染可视区域内的目录项，降低 DOM 节点数从数千个到几十个。
   - 实现 TOC 缓存机制与快速索引映射。
2. **本地正文缓存优先（Cache-First Fast Path）**：
   - 服务端 `BookCacheService` 实现离线正文缓存分片存储与元数据索引。
   - 用户打开已缓存书籍时直接走本地 SQLite / 文件系统缓存直出，实现毫秒级开书。
3. **流式搜索（SSE / WebSocket 流式推流）与 Inspector 节流**：
   - 搜索结果以流式增量推送到前端，避免等待全量书源返回。
   - 前端对高频搜索推流增加节流聚合，防止 React 渲染抖动。

## 4. 沉淀至部落知识库的经验条目
- **[性能] 缓存优先直出**：打开书籍时务必优先命中本地离线缓存（`BookCacheService`），切勿在未命中前阻塞首章正文展示。
- **[目录] 虚拟化渲染**：长篇小说目录必须采用虚拟化方案，严禁全量 DOM 挂载。
- **[流式] 搜索推流防抖**：服务端流式搜索推送高频事件时，前端应维持稳定的批量渲染节流间隔，避免高频 `setState` 导致主线程卡顿。
